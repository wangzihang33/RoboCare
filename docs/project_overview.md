# RoboCare 智能客服系统 · 项目总览与面试讲稿

## 一、项目定位

RoboCare 是面向扫地机器人和扫拖一体机器人场景的智能客服 Agent。它覆盖产品问答、使用指导、维护保养、品牌咨询、天气适配、设备使用报告和多轮故障诊断。

项目的核心不是把所有问题交给一个模型自由发挥，而是将客服请求拆成“任务路由、受限工具执行、知识检索、状态化诊断和工具治理”几个可验证的环节。用户通过 Streamlit 工作台发起会话，系统内部使用 LangChain Agent API、LangChain tools 和 middleware 完成执行。

面试时可以先用一句话概括：

> 我基于 LangChain Agent API 构建了一个扫地机器人客服系统，用规则与轻量模型完成任务路由，用 Hybrid RAG 提供产品知识，用独立的状态化诊断引擎推进多轮故障排查，再通过 middleware 对工具调用做可靠性和审计治理。

## 二、整体架构

一次请求大致经过以下链路：

```text
Streamlit 会话入口
        ↓
短期 history + session_id
        ↓
任务路由层：规则判断，冲突/模糊场景可由轻量模型兜底
        ↓
选定执行链路与工具白名单
        ├─ direct：直接回答，不调用工具
        ├─ local_rag：本地 Hybrid RAG
        ├─ web_rag：联网搜索与来源追踪
        ├─ business_query：天气或用户设备数据查询
        └─ troubleshooting：状态化故障诊断引擎
        ↓
LangChain Agent/tool middleware
        ↓
流式回答、状态更新和审计日志
```

这里需要区分两个概念：

- 项目主框架是 **LangChain**。代码直接使用 `create_agent`、LangChain tools 和 middleware。
- LangChain Agent 的底层 runtime 使用了 LangGraph 能力，但项目没有自行用 `StateGraph` 搭建另一套 LangGraph 业务架构。因此面试时应说“基于 LangChain Agent API 构建，底层由其 runtime 承载”，不要说成“项目采用 LangGraph 主导的多 Agent 架构”。

### 2.1 Agent 组装与工具白名单

前四类普通请求由同一个 Agent 工厂按路由动态组装。每个路由使用相同的基础客服提示词和 middleware，但只暴露当前路由允许的工具：

| 路由 | 主要工具 | 典型问题 |
| --- | --- | --- |
| `direct` | 无 | 问候、能力介绍、简单上下文回答 |
| `local_rag` | `rag_summarize` | 产品知识、选购、维护保养 |
| `web_rag` | `web_search` | 最新品牌、市场变化、竞品信息 |
| `business_query` | `get_weather` 或 `fetch_external_data`；报告解释阶段可补充本地 RAG | 天气适配、个人设备使用报告 |
| `troubleshooting` | 由诊断引擎调用本地诊断检索 | 故障码、故障现象和排障反馈 |

因此这不是五个完全独立的多 Agent 系统，也不是把所有工具都交给模型后再依赖提示词自律。路由选定后，`create_agent(tools=...)` 只接收对应工具集合，同时动态提示词只说明当前链路的工具边界。真正的权限边界由工具白名单决定，提示词只是帮助模型理解当前执行约束。

## 三、任务路由与执行链路

### 3.1 规则优先、轻量模型兜底

路由器维护客服领域的几组信号：报告查询、天气查询、故障现象、联网新鲜度、本地产品知识和能力介绍。规则层同时使用：

- 领域短语和否定词判断；
- 正则提取错误码、城市、用户 ID 和月份；
- 业务参数完整性校验，例如天气必须有城市，设备报告必须有用户 ID 和月份；
- 多意图冲突检测，例如同一个问题同时出现本地维护和市场对比诉求。

规则结果分为 `DECISIVE`、`NEEDS_CLARIFICATION`、`CONFLICT` 和 `NO_MATCH`：

- `DECISIVE`：已有足够证据，直接进入确定路由；
- `NEEDS_CLARIFICATION`：意图明确但缺少必要参数，先追问，不调用工具；
- `CONFLICT`：命中多个互相竞争的意图，确认用户希望优先处理哪一项；
- `NO_MATCH`：规则没有可靠命中。

在 `CONFLICT` 或 `NO_MATCH` 场景，若配置开启 `router_llm_enabled`，再调用轻量模型做语义消歧。模型必须输出受约束 JSON，证据片段必须逐字来自用户问题，路由、工具和缺失参数还会经过代码校验；模型输出不合法时回退到规则结果。这样做的价值是把确定性请求留在低成本规则路径，把真正模糊的请求交给模型，同时降低错误工具调用和无效检索。

### 3.2 路由后的提示词与工具差异

路由并不是只给请求贴一个标签。选定路由后，系统会同时完成三件事：

1. 根据 `route_tool_names()` 生成当前执行链的工具白名单；
2. 用动态 prompt 只注入当前路由的执行约束和工具说明；
3. 把路由决策、证据片段、缺失槽位和会话 ID 写入 Hook 事件，便于复盘。

例如本地知识问题只能调用 `rag_summarize`，联网问题只能调用 `web_search`，天气问题必须先有城市，设备报告必须先拿到用户 ID 和月份。故障诊断则不会继续走普通 Agent 的自由工具循环，而是交给状态化诊断引擎。

## 四、Hybrid RAG 检索优化

本地知识库承载产品说明、选购建议、维护保养和故障资料。知识文档按业务卡片切分，卡片保留 `card_id`、标题、源文件和 chunk `doc_id` 等 metadata，便于定位证据和构建评测集。加载前用文件 MD5 去重，文本再经过递归切分后写入 Chroma。

在线检索链路为：

```text
用户问题
  → qwen3.7-text-embedding 向量召回
  + jieba 分词后的 BM25 关键词召回
  → RRF 融合候选排名
  → qwen3-rerank 二阶段重排
  → Top-K 证据拼接到生成提示词
```

RRF 不直接比较向量分数和 BM25 分数，而是融合两路排名，基本形式为：

```text
score(doc) = Σ 1 / (rrf_k + rank)
```

随后把问题和候选文档一起交给 `qwen3-rerank`，从候选集合中选出最终上下文。RAG 生成链只消费当前查询和召回证据；会话历史由外层 Agent 管理，不会无条件拼进检索查询，避免把无关对话污染召回结果。

评测集采用 card-level 业务标注：每条问题记录标准卡片、来源、证据短语和关键词。指标口径如下：

- `Recall@3`：Top 3 结果中是否命中标准知识卡片；
- `MRR`：第一条相关结果排名的倒数，越靠前越高。

简历中的指标应对应具体评测报告和固定数据集；面试时要能说明数据集、命中判定和运行配置，而不是只报一个脱离评测过程的百分比。

## 五、动态 Web RAG（支撑能力）

Web RAG 仍是系统能力之一，但在简历中不作为独立核心亮点，主要用于本地知识不足或需要时效性的品牌、市场和竞品问题。

```text
Serper 搜索
 → URL 标准化、去重、来源和文件类型过滤
 → 并发抓取网页正文
 → 临时向量检索筛选相关 chunk
 → 携带 source_id/title/url 的证据生成回答
 → 写入按问题类型划分 TTL 的缓存
```

URL 治理会过滤无效链接、重复页面、PDF/图片等不适合正文抓取的来源，并限制同一域名的结果数量。网页 chunk 带来源 metadata，回答可以追溯到 URL；TTL 缓存按市场、价格、排行和维护类问题设置不同的新鲜度，平衡信息时效、成本和响应速度。

## 六、多轮故障诊断与状态管理

故障诊断是独立于普通 Agent 工具循环的状态化执行引擎。它解决的是“故障排查通常需要多轮反馈，不能每轮都从头检索、重复建议”的问题。

### 6.1 状态与持久化

每个诊断会话创建一个内部 `case_id`，状态包含：

- 设备型号、错误码、故障现象；
- 当前故障类型和当前动作组；
- 已执行动作、每次反馈结果和证据来源；
- 风险标记、轮次、澄清次数和升级原因。

外层 Streamlit 会话保留最近若干轮 user/assistant history；诊断状态则写入 SQLite 的 `diagnosis_cases` 表，使用 `session_id` 找回当前活动案例。二者职责不同：history 是对话上下文，SQLite 状态是可恢复的诊断事实和迁移位置。

升级时从状态生成 `HandoffTicket`，写入 `handoff_tickets` 表，内容包括故障摘要、设备和错误码、已尝试动作、风险标记、证据 ID 和升级原因。当前实现生成并持久化结构化交接工单，真实客服平台接口仍属于后续接入边界。

### 6.2 故障识别与本地知识检索

诊断入口按以下顺序处理：

1. 用正则提取设备型号和 `E01` 这类错误码；
2. 如果错误码在 playbook 中有审核过的定义，直接映射到已知故障类型；
3. 未知错误码本身不用于猜测故障。没有故障描述时先追问具体表现；
4. 有故障描述或没有错误码时，调用现有本地 Hybrid RAG；
5. 召回的 chunk 交给 `LLMKnowledgeResolver` 做受约束语义归一，只允许映射到现有 playbook 的故障类型。

语义归一器只接受三种判断：`MATCH`、`AMBIGUOUS` 和 `NO_MATCH`。只有“用户描述 + 召回证据”共同支持唯一故障类型，且模型置信度达到阈值、引用片段确实存在于证据原文时，才会写入 `symptom_code`。低置信度、多个类型都可能或没有证据时不会猜测，而是继续澄清；多次仍无法形成可靠诊断证据则升级人工。

这里的本地 RAG 和 playbook 不是同一层：RAG 负责从真实知识库召回证据，`config/troubleshooting.yml` 负责把已确认的故障类型编排成可执行动作组、验证条件和失败转移关系。这样既保留知识库的覆盖能力，又避免模型直接从任意 chunk 生成不受控的维修步骤。

### 6.3 动作组、观察和状态迁移

每个故障 playbook 由有依赖关系的动作组组成。例如主刷故障可以是：

```text
动作组 A：断电、拆下主刷、清理缠绕物
验证：主刷恢复转动、错误码消失
失败 → 动作组 B：检查轴承、安装位置并重启测试
失败 → 生成结构化人工交接摘要
```

引擎一次发送当前动作组，而不是一次性把所有建议塞给用户。收到反馈后，先用当前动作组的成功/失败信号做确定性判断；规则没有命中时，调用 `LLMObservationParser`。它使用低成本的 `deepseek-v4-flash` 做三分类，只能返回 `SUCCESS`、`FAILURE` 或 `UNKNOWN`，并带证据片段和置信度。模型不能直接修改诊断状态，最终状态迁移仍由引擎代码执行：

- `SUCCESS`：记录当前动作成功，诊断结束；
- `FAILURE`：记录失败，按 playbook 的 `on_failure` 转到下一动作组；
- `UNKNOWN`：不擅自推进，向用户确认结果；
- 高风险信号、用户主动要求人工或动作组耗尽：停止继续自动排查，生成交接工单。

这就是“短期对话记忆 + 持久化诊断状态 + 动作组动态编排”的实际含义，而不是简单把多轮消息拼接给模型。

## 七、Hook 生命周期治理

所有 LangChain 工具调用都经过统一 middleware，生命周期分为调用前、调用中、调用后和异常兜底四个阶段。

### 7.1 调用前：策略与可用性双重检查

`before_tool_call` 会创建或读取内部 `session_id`、`tool_call_id`，根据工具策略标记工具类型、风险等级、是否联网、是否高成本和是否访问用户数据，并检测手机号、身份证号、银行卡、邮箱、API Key、token 等敏感输入。违反策略时直接返回拦截消息，不执行真实工具。

通过策略检查后，调用中还会检查工具是否处于熔断状态。每个 Python 进程内维护工具的连续失败次数和熔断时间：可重试的超时或连接异常在限定次数内重试；连续失败达到阈值后暂时打开熔断，后续请求快速失败，恢复窗口到期再进入半开探测。当前是单进程内存实现，多实例部署时应迁移到 Redis 等共享存储。

### 7.2 调用中与调用后：可靠执行和可复盘审计

执行器为工具提供超时控制、有限重试和结果校验。结果为空、结构化结果缺少 `data` 或明确返回失败状态时，会被视为工具失败，而不是把空结果交给模型继续编造。成功后记录工具名、输入摘要、输出摘要、耗时和状态；联网搜索还会记录来源追踪信息。所有摘要经过脱敏后写入 JSONL 审计日志。

异常进入 `on_tool_error`，统一记录异常类型、错误摘要、重试次数、熔断状态和恢复动作，并向用户返回安全兜底文案，不暴露第三方 API 错误或 Python 堆栈。

因此 Hook 的升级点不是简单“多写一份日志”，而是把工具调用从“模型想调就调”变成具备策略拦截、超时重试、熔断降级、结果校验、脱敏审计和安全兜底的可恢复执行链路。

## 八、工具服务与前端边界

天气、用户设备数据、报告上下文、本地 RAG 和 Web Search 都先在 core service 层返回结构化结果，再由 LangChain tool 适配成模型可消费的文本。报告场景通过 middleware 动态切换报告提示词，并在需要时使用本地知识解释指标。

当前前端使用 Streamlit 单进程承载页面、Agent 控制器、RAG 检索、诊断状态和工具调用链路，不需要单独启动 FastAPI。`session_id` 是内部关联键，不展示给用户；真实生产环境还需要补充认证、限流、密钥托管、共享熔断存储和客服平台工单接口。

## 九、面试时的亮点对应关系

### Hybrid RAG 检索优化

重点讲 card-level 评测集、Vector + BM25 的 RRF 融合、qwen3-rerank 二阶段重排，以及 Recall@3/MRR 的计算口径。不要只说“用了向量库”，要说明为什么同时保留语义召回和关键词召回，以及如何用固定评测集验证排名质量。

### 自适应任务路由与 Agent 评测

重点讲规则层负责确定性请求，轻量模型只处理冲突和模糊意图；路由结果会驱动执行链路和工具白名单，而不只是改变一句 system prompt。评测时分别统计路由标签是否正确、工具是否属于标准工具集合，以及非法工具调用是否为零或被拦截。

### 多轮故障诊断与状态管理

重点讲诊断状态和对话 history 的职责分离、错误码精确匹配与无码/未知码场景的 Hybrid RAG 归一、动作组依赖关系、反馈观察三分类和 SQLite 持久化。最终由状态机而不是模型自由决定“结束、下一动作组或升级人工”。

### Hook 生命周期治理

重点讲调用前敏感信息和工具策略拦截、调用中的超时/有限重试/熔断、调用后的结果校验与脱敏审计，以及异常时的安全兜底。面试官追问熔断时，应说明当前实现是进程内状态，并主动指出多实例生产环境需要共享存储。

## 十、指标使用边界

简历中的 `Recall@3`、`MRR`、路由准确率、工具选择准确率、诊断任务完成率和无效重复建议率，都应绑定到固定评测集、运行配置和报告文件。面试时可以解释指标如何计算，但不要把尚未重新运行或仅用于方案讨论的模拟结果描述成线上生产指标。
